# إدارة المالك الكاملة — وثيقة التصميم

**التاريخ:** 2026-11-25  
**الحالة:** جاهزة لطلب الموافقة النهائية؛ لا تنفيذ قبل الموافقة  
**النطاق:** بوابة المالك في الواجهة الثابتة `web/` + Supabase

## 1. الهدف ولماذا

لوحة المالك الحالية تعرض بيانات حقيقية لكنها لا تمنح المالك صلاحيات الإدارة التي يطلبها. ثلاث مشاكل ظاهرة:

1. زر «إضافة مستخدم» في لوحة التحكم مجرد رابط يفتح صفحة مكتوب فيها «قراءة فقط»؛ لا يوجد نموذج إنشاء ولا تعديل ولا حذف.
2. زر «إنشاء مقرر» في أعلى صفحة المقررات يكشف نموذجاً موجوداً أسفل القائمة فقط، ولا ينفّذ الإنشاء في مكانه.
3. صفحة الطلاب تملك حقل معرّف واحداً وتستدعي `management_enroll_student` فقط؛ لا إنشاء طالب، لا اختيار مسار، لا نقل بين مقرر أو مسار، لا إيقاف أو حذف تسجيل.

الهدف تحويل بوابة المالك إلى بوابة إدارة فعلية كاملة، مع بقاء الأستاذ مقيّداً بـ `teacher_create_assignment` فقط، وكل عمليات الكتابة الأخرى بـ `management_*` محمية بـ `public.is_owner()`.

## 2. الوضع الحالي المؤكد بالفحص

- `web/src/pages/owner/dashboard.js:17-22` يعرّف أربعة إجراءات كروابط `href` فقط، بلا معرّفات أو معالجات.
- `web/pages/owner/users.html:25` ينص صراحة على «قراءة فقط»؛ `users.js` يרבط التصفية والتحديث فقط.
- `web/src/pages/owner/courses.js:105-111` يضيف زراً أعلى الصفحة يخفي/يظهر `ocFormPanel` الواقع بعد القائمة في `courses.html:39-66`.
- `web/src/pages/owner/students.js:60-81` يستدعي `management_enroll_student` فقط.
- Supabase لا يملك حالياً أي RPC لإنشاء مستخدم، تعديله، حذفه، تغيير دوره، تغيير مساره، نقل تسجيل، أو حذف مقرر.
- الموجود فعلاً: `management_create_course`, `management_update_course`, `management_assign_course_teacher`, `management_enroll_student` (في `0112`/`0113`).
- نموذج الدخول الحالي يحول الرقم/الرمز إلى `<platform_id>@staff.local` أو `<platform_id>@students.local` عبر `0103_login_identifier_resolver.sql`، و`legacy-login` ينشئ حسابات Auth بالبريد المشتق نفسه.
- تسجيلات البكالوريوس في البيانات الحقيقية تشمل المقرر الأصلي `bachelor` وفرع الجنس `bachelor_m` أو `bachelor_f` معاً (`0013_scope_law211_enrollments.sql`).
- إنشاء حساب Supabase Auth يحتاج `service_role`؛ لا يمكن ولا يجوز وضعه في حزمة المتصفح المنشورة على GitHub Pages.

## 3. الأهداف

- إضافة مستخدم بالأدوار الموجودة فعلاً: `teacher`، `assistant`، `student`. لا يُنشأ مالك إضافي.
- تعديل بيانات المستخدم، تفعيله/تعطيله، إعادة تعيين كلمة مروره، وحذفه بعد معاينة أثر الحذف.
- إنشاء مقرر وتعديله وأرشفته وحذفه، مع إسناد الأستاذ، من أعلى الصفحة دون تنقّل غير مفهوم.
- إنشاء طالب جديد، تسجيل طالب موجود في مقرر أو مسار، نقله بين مقررات أو مسارات، تعديل مساره/مستواه، إيقاف أو حذف تسجيله.
- الحفاظ على كل الأزرار والوظائف الحالية وإضافة الجديد إليها لا استبدالها.
- تسجيل كل عملية إدارة في `audit_logs` عبر دوال `security definer`.

## 4. القرارات والضوابط

### 4.1 قرارات متفق عليها

- **الدخول:** يُحافظ على الدخول بالرمز كما هو. حساب Auth يُنشأ ببريد مشتق من `platform_id` مثل `TE0007@staff.local` أو `BM0012@students.local`. البريد الحقيقي الذي يُدخله المالك يُخزَّن في `users.email` للمراسلة فقط، ولا يغيّر بريد الدخول. لذلك لا يُعدَّل `0103`، ولا تُضاف صلاحية دخول بالبريد الحقيقي في هذا النطاق.
- **الحذف النهائي:** يُسمح بحذف المستخدم والمقرر نهائياً بعد تأكيد صريح يعرض عدد السجلات المتأثرة. يُمنع حذف المالك الحالي، ويُمنع حذف مستخدم مسند إليه مقررات أو مؤلفات إلا بعد إعادة الإسناد. سجلات `audit_logs` لا تُعدّ تبعية مانعة لأنها سجل تاريخي و`actor_id` يصبح فارغاً عند الحذف. بقية السجلات التابعة تُحذف بقواعد قاعدة البيانات الحالية بعد العرض والموافقة.
- **نقل الطالب:** يُبقى التسجيل القديم بحالة `suspended` وتبقى الدرجات والحضور والتسليمات والنقاط محفوظة، ويُفعَّل التسجيل في المسار أو المقرر الجديد. لا يُحذف سجل أكاديمي سابق بسبب النقل.
- **تعطيل المستخدم:** لا يكتفي بعلم `users.is_active`؛ Edge Function يحظر جلسات Auth فوراً عند التعطيل ويزيل الحظر عند التفعيل.

### 4.2 ضوابط مانعة

- لا تغيير في بوابة الأستاذ؛ تبقى للقراءة وإنشاء الواجبات في مقرراته المسندة فقط.
- لا تغيير في بوابة المساعد؛ تبقى للعرض والتصدير.
- لا بيانات تجريبية، لا أسماء مالك ثابتة، لا كلمات مرور أو مفاتيح في الكود أو Git.
- لا إحياء خادم Express/EJS؛ الواجهة الثابتة هي الإنتاج وExpress أرشيف محلي فقط.
- لا نشر GitHub Pages ولا تطبيق ترحيل قاعدة البيانات ولا نشر Edge Function قبل موافقة صريحة بعد التحقق.
- لا تنفيذ `npm run deploy:dev`.

## 5. المسارات التي درستها الوثيقة

### المسار 1 — Edge Function + ترحيل `0114` (المختار)

دالة خلفية تتحقق من JWT المالك وتستدعي حارس مالك مكتوب في SQL، ثم تستخدم `service_role` لعمليات Auth فقط. بيانات المنصة تُكتب عبر دوال `management_*` بالجلسة العادية للمالك، فتعمل حماية `auth.uid()` داخل الدوال كما هي. الواجهة لا ترى أي سر.

**المزايا:** يحقق كل الصلاحيات المطلوبة دون كسر نموذج RLS الحالي، ويبقي الحسابات وبيانات المنصة متسقة.  
**العيب:** يحتاج تطبيق ترحيل ونشر دالة خلفية، وكلاهما يتطلب موافقة قبل التنفيذ في الإنتاج.

### المسار 2 — SQL فقط داخل `0114`

كتابة مباشرة في `auth.users` من دالة `security definer`.

**المزايا:** لا يحتاج نشر دالة خلفية منفصلة.  
**العيب:** هش في تجزئة كلمات المرور والجلسات وتأكيد البريد، ويمكن أن ينتج حسابات لا تستطيع GoTrue تسجيلها. **مرفوض.**

### المسار 3 — إحياء Express/service_role القديم

**مرفوض** لأنه يعاكس قرار اعتماد الواجهة الثابتة على GitHub Pages ويُعيد خادماً أرشيفياً كمسار إنتاج.

## 6. التصميم المختار

### 6.1 ترحيل `supabase/migrations/0114_owner_full_management.sql`

كل الدوال `security definer` مع `set search_path = public`، تتحقق من `public.current_user_id()` و`public.is_owner()`، وتُسجّل في `audit_logs`. الصلاحيات تُسحب من `public, anon` وتُمنح لـ `authenticated` فقط، عدا حارس الـ Edge Function فيُمنح لـ `service_role` فقط. يُرفق الترحيل بملف `supabase/rollback/0114_owner_full_management_rollback.sql` لحذف الدوال عند الحاجة.

**دوال الحسابات**

- `public.is_owner_by_auth_uid(p_auth_uid uuid) returns boolean`: حارس يستخدمه الـ Edge Function بعد التحقق من JWT؛ يطابق `users.auth_id` ويطبّق نفس منطق `public.is_owner()`. يُمنح لـ `service_role` فقط.
- `public.management_allocate_platform_id(p_role text, p_track text) returns text`: يحسب الرمز التالي تحت قفل استشاري، بالبادئة `TE` للأستاذ و`AS` للمساعد و`BM/BF/EQ/EX/PG` للطالب حسب المسار. لا بادئة `AD` للمستخدمين الجدد. التفرد النهائي محمي بالفهرس الفريد على `lower(platform_id)`.
- `public.management_create_user_profile(...)`: ينشئ صف `users` بعد إنشاء حساب Auth. يستقبل `p_auth_id` و`p_platform_id` المحسوبين مسبقاً وبيانات الاسم والبريد الحقيقي والهاتف والدور والمسار والمستوى والرقم الجامعي والوظيفة. يمنع تكرار `auth_id` وينشئ `must_change_password=true`.
- `public.management_update_user(...)`: تعديل الاسم والبريد الحقيقي والهاتف والرقم الجامعي والمسار والمستوى والنوع والوظيفة والدور والرمز. يمنع تغيير دور المالك أو تعطيل نفسه، ويمنع منح بادئة `AD`، ويُزامن الدور مع `is_staff` والحقول الخاصة بالطالب. أي تغيير في الدور أو الرمز يستدعي لاحقاً `sync_auth_identity` في Edge Function حتى يستمر الدخول بالرمز الجديد.
- `public.management_set_user_active(p_user_id bigint, p_active boolean)`: يضبط `users.is_active` مع منع تعطيل المالك الحالي. التنفيذ الكامل للتعطيل يتم بالاقتران مع عملية `set_active` في Edge Function.
- `public.management_flag_password_change(p_user_id bigint, p_value boolean)`: يضبط `must_change_password` بعد إعادة التعيين.
- `public.management_preflight_delete_user(p_user_id bigint) returns jsonb`: يعيد أعداد التسجيلات والدرجات والتسليمات والحضور والنقاط والإشعارات والمقررات المسندة والمؤلفات، مع أسباب المنع إن وُجدت. الواجهة تعرض هذه الأعداد قبل تأكيد الحذف.
- `public.management_delete_user_finalize(p_user_id bigint, p_expected_auth_id uuid)`: يحذف صف `users` بعد فحص تبعيات مطابق للفحص السابق، مع استثناء `audit_logs` و`created_by` و`archived_by` و`uploader_id` التي تصبح قيمتها `null` تلقائياً. يُخزَّن `p_expected_auth_id` في `audit_logs` قبل حذف Auth حتى تبقى إعادة المحاولة ممكنة لو صار `users.auth_id` فارغاً بعد الحذف.

**دوال المقررات**

- تُعاد تعريف `public.management_update_course` ليقبل `p_code` اختيارياً مع التحقق من التفرد، مع إسقاط التوقيع القديم صراحةً حتى لا يبقى إصداران متوازيان. تبقى أزرار التعديل والأرشفة تعمل كما هي.
- `public.management_preflight_delete_course(p_course_id bigint) returns jsonb`: يعيد أعداد المقررات الفرعية والمحاضرات والاختبارات والواجبات والتسجيلات والتسليمات والدرجات والحضور والنقاط. حذف الأصل يعني حذف فروعه بالقاعدة الحالية، لذلك تُعرض الأعداد قبل التأكيد.
- `public.management_delete_course(p_course_id bigint)`: يحذف المقرر وكل تبعياته بقواعد `on delete cascade` الحالية بعد الفحص المسبق والتأكيد، ويسجّل الأعداد في `audit_logs`. لا يُمنع بسبب إسناده إلى أستاذ.

**دوال الطلاب والتسجيل**

- `public.management_change_student_track(p_student_id bigint, p_track text, p_level smallint, p_sync_enrollments boolean)`: يغيّر مسار الطالب ومستواه. عند `p_sync_enrollments=true` يُوقف التسجيلات القديمة بدل حذفها، ويُنشئ تسجيلات نشطة للمسار الجديد. `bachelor` مسموح للمقررات فقط ولا يُقبل كمسار حساب طالب.
- `public.management_enroll_student_in_track(p_student_id bigint, p_track text, p_level smallint)`: يسجّل الطالب في مقررات المسار/المستوى المحددين مع استبعاد المؤرشفة. لطلاب `bachelor_m`/`bachelor_f` يشمل المقرر الأصلي `bachelor` وفرع الجنس معاً، وفق النمط المطبّق في `0013`. لبقية المسارات يسجّل في مقررات المسار مباشرة.
- `public.management_transfer_student(p_student_id bigint, p_from_course_id bigint, p_to_course_id bigint)`: يُوقف تسجيل المقرر القديم ويُفعّل تسجيل المقرر الجديد مع بقاء الدرجات والسجلات السابقة.
- `public.management_set_enrollment_status(p_course_id bigint, p_student_id bigint, p_status text)`: إيقاف/إعادة تفعيل تسجيل مقرر واحد دون لمس `users.is_active`.
- `public.management_remove_enrollment(p_course_id bigint, p_student_id bigint)`: يحذف التسجيل فقط إذا لم تكن هناك درجات أو تسليمات أو حضور أو نقاط مرتبطة؛ وإلا يُوقفه ويُخبر الواجهة أن الحذف الكامل غير متاح حفاظاً على السجل الأكاديمي.
- تُعاد تعريف دوال `0112`/`0113` الحالية بالتواقيع نفسها لإضافة كتابة `audit_logs` دون تغيير سلوكها، عدا `management_update_course` كما بيّن أعلاه.

### 6.2 Edge Function `supabase/functions/owner-user-admin/index.ts`

- يستقبل POST مع `Authorization: Bearer <access_token>` من جلسة المالك مع `apikey`.
- يتحقق من التوكن عبر عميل anon، ثم يستدعي `is_owner_by_auth_uid` بصلاحية `service_role`. أي فشل يُعيد `{ ok:false, error:'not_allowed' }`.
- جميع استدعاءات RPC لبيانات المنصة تتم بالتوكن الأصلي للمالك، لا بـ `service_role`، حتى تبقى حماية `auth.uid()` فعّالة داخل الدوال. `service_role` يُستخدم فقط في عمليات Auth Admin.
- العمليات: `create`، `reset_password`، `ensure_auth`، `sync_auth_identity`، `set_active`، `delete_user`. لا توجد عملية `update_email` للبريد الحقيقي لأنه بيانات مراسلة فقط.
- كلمة المرور المؤقتة تُولَّد في المتصفح عبر `crypto.getRandomValues` من أبجدية بلا رموز ملتبسة، وتُعرض مرة واحدة، ولا تُخزَّن في السجلات أو قاعدة البيانات.
- ترتيب الإنشاء: يتحقق المالك من الرمز عبر `management_allocate_platform_id`، ثم يستدعي Edge Function بذلك الرمز لإنشاء Auth بالبريد المشتق، ثم تستدعي الدالة `management_create_user_profile` بتوكن المالك مع `p_auth_id`. إن فشل إنشاء الصف تحذف الدالة حساب Auth تعويضاً.
- `ensure_auth`: للحسابات القديمة التي `auth_id` لها فارغ؛ تنشئ حساب Auth بالرمز الحالي وكلمة مؤقتة ثم تربطه بصف `users`.
- `sync_auth_identity`: عند تغيير الدور أو `platform_id` يحدّث بريد Auth المشتق و`app_metadata` ليظل الدخول بالرمز الجديد صالحاً.
- `set_active`: يضبط `ban_duration` في Auth عند التعطيل ويزيله عند التفعيل، ويستدعي `management_set_user_active` بتوكن المالك.
- ترتيب الحذف النهائي: `management_preflight_delete_user` أولاً، ثم تسجيل معرّف Auth في `audit_logs`، ثم حذف حساب Auth، ثم `management_delete_user_finalize` بتوكن المالك. إن فشلت الخطوة الأخيرة تبقى رسالة واضحة وإمكانية إعادة المحاولة باستخدام المعرّف المسجّل، ولا يُعرض المستخدم كأنه حُذف.
- لا توجد أي قيمة `service_role` في `web/` أو في أي التزام Git.

### 6.3 واجهة `web/`

**لوحة التحكم**

- إجراء «إضافة مستخدم» يفتح `pages/owner/users.html?new=1`، و«إنشاء مقرر» يفتح `pages/owner/courses.html?new=1`. التقرير والدليل يبقيان روابط عادية.

**المستخدمون**

- زر «إضافة مستخدم» أعلى الصفحة يفتح نموذجاً في نفس الصفحة. الحقول: الاسم، البريد الحقيقي للمراسلة، الهاتف، الدور، المسار والمستوى للطالب، الرقم الجامعي، الوظيفة، وكلمة مرور مؤقتة. يعرض النموذج الرمز الذي سيُستخدم للدخول بعد حجزه. يبقى زر التحديث والتصفية كما هو مع إصلاح spinner المفقود.
- كل صف يحصل على إجراءات: تعديل، تفعيل/تعطيل مع حظر الجلسات، إعادة تعيين كلمة مرور، إنشاء حساب دخول للحسابات القديمة، وحذف نهائي بعد معاينة الأثر.
- تغيير الدور أو الرمز يعرض تنبيهاً بأن بريد الدخول المشتق سيتحدث تلقائياً.

**المقررات**

- يُنقل `ocFormPanel` إلى ما بعد قسم الإجراءات مباشرة، ويُفتح ويتلقى التركيز عند الضغط على الزر العلوي أو عند `?new=1`، بدل ظهوره أسفل القائمة.
- تبقى أزرار التعديل والأرشفة، ويُضاف زر حذف يعرض عدد المقررات الفرعية والمحاضرات والاختبارات والتسجيلات قبل التأكيد.
- حقل الرمز يصبح قابلاً للتعديل فعلياً عبر RPC الجديد بدل أن يبدو قابلاً للتعديل ثم يُتجاهل.

**الطلاب**

- أعلى الصفحة: «طالب جديد»، «تسجيل طالب موجود»، «نقل طالب»، «تغيير المسار».
- نموذج الطالب الجديد ينشئ الحساب ثم يسجّل الاختياري في مقرر أو مسار محدد.
- قائمة المقررات تُجمّع حسب المسار والمستوى، مع فلتر مسار، بدل قائمة واحدة غير مصنّفة. تسجيل المسار لـ `bachelor_m`/`bachelor_f` يضيف الأصل والفرع معاً.
- تسجيل الطالب الموجود يحتفظ بالحقل الحالي ويضيف اختيار المسار.
- جدول الطلاب يحصل على إجراءات لكل صف: تسجيل، نقل، تغيير مسار/مستوى، إيقاف تسجيل، حذف تسجيل محمي، وإعادة تعيين كلمة مرور.
- النقل وتغيير المسار يُظهران تنبيهاً بأن السجل القديم سيُوقف لا يُحذف.

## 8. ما يقرره المنفّذ دون الرجوع للاستخدام

شكل اللوحات الداخلية (inline panels أم modal)، التسميات الدقيقة للأزرار، ترتيب الحقول، ورسائل النجاح والخطأ، طالما بقيت عربية RTL وتخدم نفس السلوك. أي تغيير في الصلاحيات، أو في سياسة الحذف، أو في ترتيب الحذف والإنشاء يحتاج موافقة جديدة.
